The Fundamental Difference: Antigravity vs Codex vs Claude

Codex and Claude Code natively support usage querying: Codex exposes account/rateLimits/read and pushes account/rateLimits/updated via its app-server JSON-RPC. Claude streams rate_limit_event and has get_usage in its SDK.

Google Antigravity uses generic ACP (Agent Client Protocol) over stdio. Google's ACP implementation exposes zero quota or usage methods.

Why REST Probing Fails (Tested Live with User OAuth Token)

We extracted the user's active Google OAuth token from acp_token.json (which holds https://www.googleapis.com/auth/aicode and https://www.googleapis.com/auth/cloud-platform) and probed Google's endpoints:

  • https://aicode.googleapis.com/v1main:fetchQuotaStatus → 404 Not Found
  • https://agentaicode.googleapis.com/v1main:fetchQuotaStatus → 404 Not Found
  • https://businessaicode.googleapis.com/v1main/...:fetchQuotaStatus → 404 Not Found

Finding: Google does not expose FetchQuotaStatus over public HTTP/1.1 REST gateways. It is an internal HTTP/2 gRPC service hosted on agentaicode.googleapis.com:443. Furthermore, agy.EXE does not contain any CLI command or ACP RPC handler to invoke this method externally; the protobuf bindings are compiled in solely as part of Google's internal proto bundle.

3. Why the Current Multi-Machine Display Failed

The user observed conflicting metrics across machines sharing the exact same Google account: 

cc-3:   Session 100% | resets now    | Daily 0% resets in 8h 38m
cc-1:   Session 0%   | resets now    | Daily 0% resets in 8h 34m
BRAVO:  Session 40%  | resets in 4h  | Daily 0% resets in 23h 14m

The root causes are 100% diagnosed in the codebase:

  1. Isolated In-Memory Counters: In antigravityUsageLimits.ts, tokens are accumulated in a local JavaScript Ref in server RAM. Each machine only knows about the turns executed on that single physical host.
  2. Independent Synthetic Timers: When a server starts, it initializes a local 5-hour window timer (now + 5 hours). Because BRAVO, cc-1, and cc-3 booted at different times, their reset clocks are completely out of sync.
  3. Isolated Rate-Limit Lockout: When cc-3 encountered an HTTP 429 from Google, only cc-3 set its local state to 100%. cc-1 and BRAVO had no idea that the shared Google account was throttled.

4. The Implementation Blueprint (Strategy A – Recommended)

To provide real, accurate, and synchronized usage tracking across all machines without depending on fragile reverse-engineered Google gRPC internals:

1. Cross-Machine Usage Sync

Store Antigravity token usage and rate-limit states in a shared SQLite store or broadcast via the existing T3 multi-machine pairing mesh (WebSocket).

Every token spent on CC-1, CC-3, or BRAVO increments the same global account counter.

2. Synchronized 429 Lockout

When any machine receives a Google 429 (RESOURCE_EXHAUSTED), it parses the exact Retry-After header or Google error metadata.

It immediately broadcasts a 100% usage lockout and exact reset timestamp to all connected machines.

Step-by-Step Implementation Plan:

  1. State Persistence (antigravityUsageStore.ts): Persist usage snapshots to disk (or SQLite) keyed by Google account email. Multiple machines sharing the data directory or syncing via T3 multi-machine sync will read the same shared state.
  2. Network Synchronization: Add an IPC/RPC message across paired T3 nodes: provider/usage/sync. When machine A finishes a turn, it broadcasts { provider: 'antigravity', email, addedTokens, timestamp }.
  3. Unified Reset Anchor: Instead of now + 5h per machine, anchor the 5-hour window to fixed global UTC boundaries (e.g. 00:00, 05:00, 10:00 UTC) matching Google's standard billing buckets.

5. Alternative: Pursuing Raw Google gRPC (Strategy B)

If the user insists on querying Google's servers directly for the exact protobuf percentage:

  • Requirement: Compile Google's PredictionService protobuf files into TypeScript using ts-proto or @grpc/grpc-js.
  • Connection: Open a secure HTTP/2 gRPC channel to agentaicode.googleapis.com:443.
  • Headers: Supply Authorization: Bearer <access_token>, x-goog-user-project: aicode-consumers, and Google internal client metadata.
  • Risk Assessment: High likelihood that Google's frontend proxy rejects non-internal callers or updates RPC signatures without notice.
Conclusion

Implementing Strategy A (Shared Cross-Machine Usage & 429 Broker) is completely feasible within 1–2 days, solves 100% of the discrepancy between BRAVO, cc-1, and cc-3, and guarantees unified countdowns and lockouts across all machines.
