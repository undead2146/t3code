AGCP (Antigravity ACP) Fast Startup & Resilient Session Continuation

Architecture & Implementation Plan Subsystem: Server / Providers Target: Windows / Electron & Server Zero 40s Delay
Executive Summary: Migrating from the legacy native CLI (agy.exe) to the Agent Client Protocol (agy_acp_server.exe) introduced a 40-second cold launch delay and caused running threads to instantly fail upon server restart. This plan details the root causes—PyInstaller cold-unpack overhead, disposable probe spawns, pessimistic initial drafts, and ungated session reconciliation—and provides an amicable 4-step architectural remedy.

1. The Problem: Legacy CLI vs. AGCP Protocol

Metric / Characteristic Legacy agy.exe (CLI) Current agy_acp_server.exe (AGCP) Optimized Target State
Executable Size & Nature ~15MB native compiled Go/Rust binary 297MB PyInstaller bundle + 122MB localharness Same binary, but instant caching & lazy spawn
Startup / Probe Delay <50ms (agy --version stdout) 25s – 45s (throwaway RPC probe) <5ms (optimistic disk validation)
Initial Provider Status Instantly ready if found Starts as warning ("Checking...") Starts as ready if token & models cached
Thread Survival on Restart Clean process spawn Fails immediately due to probe thrashing 100% resilient with readiness gating & retry

2. Root Cause Analysis

Cause 1 Disposable Probe Spawns
On boot, AntigravityDriver.probe cold-spawns a 300MB PyInstaller binary in stateDir just to run runtime.initialize(). Once initialized, it immediately terminates the process. This throwaway spawn burns 30-40 seconds of disk I/O and Windows Defender inspection for zero ongoing utility.
Cause 2 Pessimistic Initial Draft
In makeAntigravityProvider, the initial snapshot hardcodes status: "warning", installed: false, and auth.status: "unknown". It ignores the fact that .install-complete.json, acp_token.json, and models.json already exist on disk, forcing the UI to lock up in a waiting state.
Cause 3 Startup Process Thrashing
When restarting with running threads, T3 Code simultaneously spawns: (1) The disposable probe process, (2) A session process for the continuing thread, and (3) A standby prewarm process. Three 300MB PyInstaller binaries compete for %TEMP% unpacking locks, spiking disk and CPU to 100%.
Cause 4 Ungated Session Reconciliation
reconcileProviderSessions immediately fires providerService.sendTurn without waiting for provider readiness. If sendTurn hits a timeout during the concurrency storm, it immediately calls settleAsError, killing the thread forever with "Could not continue this thread after the server restart".

3. Implementation Solution Architecture

Phase 1: Instant Optimistic Readiness on Startup (<5ms)

Eliminate the 40-second blank waiting state by validating cached assets synchronously on boot before publishing the initial provider snapshot.

  • File: apps/server/src/provider/Layers/AntigravityProvider.ts & apps/server/src/provider/Drivers/AntigravityDriver.ts
  • Check synchronously on disk:
    1. installation.resolve() verifies .install-complete.json and binary existence (<1ms).
    2. fileSystem.exists(acp_token.json) verifies authentication (<1ms).
    3. readCachedModels(models.json) supplies discovered model list (<1ms).
  • When all 3 are present, initialDraft initializes directly with: 
    installed: true,
status: "ready",
auth: { status: "authenticated", type: "oauth-personal", label: "Google account" },
models: cachedModels,
version: release.version
  • Impact: Antigravity is connected and ready on Frame 1 of launching T3 Code. No 40s waiting bar.

Phase 2: Bypass Disposable Startup Health Probes

Avoid spawning disposable throwaway PyInstaller instances when the environment is already known to be sound.

  • File: apps/server/src/provider/Drivers/AntigravityDriver.ts
  • If the binary and valid auth token exist on disk, the startup probe returns immediate success using the resolved installation release metadata.
  • A live ACP session is only spawned when the user actually sends a turn or continues a thread, eliminating redundant cold-boots.
  • Cache Browser Preflight: In prepareAntigravityProfile, cache the t3code.exe -e ... browser suppression verification per process lifetime so subsequent session launches don't re-spawn helper processes.

Phase 3: Prewarm Throttling & Concurrency Protection

Prevent PyInstaller spawn pile-ups on Windows.

  • File: apps/server/src/provider/Layers/AntigravityAdapter.ts
  • Guard prewarm(cwd) so that it does not trigger concurrently while an active session is recovering or starting.
  • Defer prewarming until the main session has successfully completed initialization and settled into an idle state.

Phase 4: Provider Readiness Gating & Resilient Retry in Session Reconciliation

Ensure that active turns survive server restarts and restarts do not corrupt running threads.

  • File: apps/server/src/serverRuntimeStartup.ts (in reconcileProviderSessions)
  • Readiness Await: Before triggering providerService.sendTurn, await provider readiness with a grace period (e.g., up to 30s timeout) instead of dispatching into a cold provider immediately.
  • Continuation Retry Policy: Wrap the continuation dispatch with a retry loop (3 attempts with exponential backoff: 2s, 4s, 8s) if a transient connection error occurs.
  • Graceful Fallback: If continuation still fails after retries, preserve the thread's message history and set the session to "stopped" or "ready" rather than a destructive permanent "error".

4. Phased Verification & Validation Plan

Verification Strategy:
  • Unit Test: Test AntigravityProvider initial snapshot generation with cached token and models in AntigravityProvider.test.ts.
  • Reconciliation Test: Add a test case in serverRuntimeStartup.reconcile.test.ts simulating a provider that becomes ready asynchronously after boot, verifying continuation succeeds without error.
  • End-to-End Latency: Measure server boot time to provider ready state (expected drop from ~42s down to ~15ms).
  • Full Typecheck & Vitest: Run pnpm --filter @t3tools/server test and project-wide typecheck.
